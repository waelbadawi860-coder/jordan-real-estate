New automated tests: `web/tests/db/qa.test.ts` (16 tests). All suites after the fixes:

| Suite | Result |
|---|---|
| Unit | 51/51 pass |
| Database (includes the 16 new QA tests) | 113/113 pass |
| Site tests on the local dev server | 52/52 pass (before this QA round) |

Result key: **Pass** = works as the matrix expects. **Fixed** = gap found and fixed in this round. **Finding** = works, but differs from the matrix; owner decision. **N/A** = the feature doesn't exist yet.

## 1. Listing lifecycle

| Check | Result | Evidence |
|---|---|---|

| Oversized file (> 5 MB) | **Pass** | Refused by storage. |

## 3. Promotions

| Check | Result | Evidence |
|---|---|---|
| Grant / extend / revoke "featured" | **Pass** | Extending adds to the remaining time. Each step is stored with the admin who did it, the amount and the payment reference. Sellers can't promote themselves. |
| Expiry at the exact moment | **Pass** (database) / **Finding** (display) | The database stops counting it as featured the second it expires. Cached lists may still show the "featured" box for up to a few minutes after that. |

## Recommendations (owner decisions)

1. **Automatic hold after reports:** for example, hold an ad for review once 3 *different* users report it within 24 hours, and notify the admin. Risk: competitors could mass-report. Requiring different accounts and the per-user report limit reduces that.
2. **Bulk actions in admin** (approve/reject several pending ads at once): when daily volume justifies it.
3. **Office CSV import:** when offices with many listings join.
4. **Online payments:** when added, test declined cards, dropped connections and duplicate callbacks (idempotent payment records).
